# Инструкция для планировщика (нейросеть на ПК2)

Этот документ — для нейросети-планировщика (например, GPT), которая ведёт проект через GitHub, и для человека, который её настраивает.
Исполнитель — JustAI на ПК1: он берёт задачи из issues, пишет код, запускает проверки и тесты, отвечает в issues.
Как настроить сам мост — [github-bridge.md](github-bridge.md).

Есть два способа работать планировщиком:

- **A. JustAI на ПК2, профиль Architect.** Все действия ниже — инструменты (`github_create_task`, `github_e2e`, `github_merge_task` и др.). Инструкции уже встроены в профиль; раздел 4 ниже — справка.
- **B. Любая нейросеть с доступом к GitHub** (веб-чат с GitHub-интеграцией, свой скрипт). Всё делается текстом issues. Скопируйте ей промпт из раздела 2.
- **C. Нейросеть, которая GitHub только читает** (подключение веб-чата без права создавать issues — `createIssue → 403`). Она пишет план текстом в формате «### ISSUE» (раздел 2а), человек вставляет его в ленту моста на ПК1 — JustAI сам создаёт все issues. Отчёты и результаты она читает в репозитории как обычно.

## 1. Команды

Все команды пишутся **отдельной строкой** в описании issue (или в комментарии к задаче, если планировщик умеет комментировать). ПК1 проверяет GitHub раз в минуту и выполняет всё по очереди; служебный issue с командой после ответа закрывается.

| Что нужно | Issue (работает всегда) | Комментарий к задаче | Ответ |
|---|---|---|---|
| Новая задача | заголовок `[justai] …` | — | ход работы и отчёт в этом issue, PR |
| Задача после других | строка `Depends on #3, #4` в задаче | — | начнётся, когда #3 и #4 слиты |
| Правки к чужому PR | строка `Base: #113` в задаче | — | ветка задачи — от ветки PR #113, её PR — в эту ветку |
| Проверить формат сценариев | `/justai e2e #N check` | `/justai e2e check` | таблица: какие `tests/e2e/*.yml` разобраны, ошибки с номером шага (без запуска) |
| Правки | `/justai #N` + текст правок ниже | текст правок | новый отчёт в задаче |
| **Проверить приложение** | `/justai e2e #N` + блок ```yaml со `steps:` | `/justai e2e` + блок | таблица шагов ✓/✕, скриншоты, консоль, разница с прошлым |
| Прогнать все сценарии проекта | `/justai e2e #N all` | `/justai e2e all` | отчёт по каждому файлу `tests/e2e/*.yml` |
| Запустить приложение и держать | `/justai app start #N` (`status`, `logs`, `stop`) | `/justai app start` | адрес, вывод приложения |
| Выполнить команду | первая строка `/justai run #N npm test` | `/justai run npm test` | код выхода и вывод |
| Остановить | `/justai stop #N` | `/justai stop` | «остановлен», метка `justai:paused` |
| Продолжить | `/justai continue #N` + указания | указания | продолжает в той же сессии |
| Принять и слить | `/justai merge #N` | `/justai merge` | «слит в main» или причина отказа |
| Закрыть ненужные issues | `/justai close #2 #3 #10` | — | «закрыты …» |
| Жив ли мост, что в очереди | `/justai status` | — | время ПК1, задачи, приложение, режим сна |

`#N` — номер задачи: команда выполняется в её ветке (если ветку уже слили и удалили — в основной). Для `e2e`, `run`, `app` это может быть и номер открытого PR этого репозитория — тогда используется ветка PR. Без `#N` — основная ветка.

Переносы строк должны быть настоящими. Текст, где весь перенос — символы `\n`, JustAI раскроет сам, но надёжнее писать по-настоящему многострочно.

Метки: `justai:working` — делается, `justai:review` — готов PR, `justai:failed` — не вышло, `justai:paused` — остановлено (по команде или «🚧 заблокирована»), `justai:merged` — слито.

- **🚧 Заблокирована, требуется решение** — агент перечитывал уже прочитанные файлы и ничего не менял; JustAI остановил его сразу, а не через час. Ответьте точными заменами или полным текстом файла (JustAI продолжит в той же сессии) или разбейте задачу.
- **⏳ Модель не отвечает** — сбой локальной модели (или сети до GitHub), а не задачи: задача не проваливается, сделанное сохраняется в ветке, и она продолжается сама (зависшую Ollama JustAI перезапускает). До 6 попыток подряд, потом — `failed` с причиной. Не шли в это время `continue` к этой задаче: правки к ней применятся после. Команды без модели (`stop`, `close`, `run`, `e2e`, `merge`, `status`) работают.
- `Base: #N` можно написать и в `/justai continue #M`: ветка PR #N вольётся в ветку задачи, PR задачи перенаправится в неё.
- В отчёте **«Факты по git»**: что изменено **в этом запуске** и что **всего в ветке** — отдельно. «В этом запуске файлы не менялись» не значит, что в PR нет правок. Причина остановки и последняя ошибка инструмента — дословно из лога; «Отчёт агента» — его слова.

## 2. Промпт для нейросети-планировщика (вариант B)

Скопируйте целиком, заменив `ВЛАДЕЛЕЦ/РЕПОЗИТОРИЙ`.

````
Ты — ведущий разработчик и планировщик проекта в репозитории ВЛАДЕЛЕЦ/РЕПОЗИТОРИЙ.
Сам ты код не пишешь. Код пишет и запускает агент JustAI на другом компьютере (ПК1): он берёт задачи из GitHub issues,
делает каждую в отдельной ветке, открывает pull request и отвечает в issue. Ты общаешься с ним только через issues.
Все команды — отдельной строкой в описании нового issue. ПК1 проверяет GitHub раз в минуту и делает всё по очереди.
Одна команда — один issue. Пиши настоящие переносы строк, не символы «\n».
Код и исправления в репозиторий сам не вноси (не коммить, не создавай ветки и PR) — всё делает JustAI по твоим issues.
Полная справка: docs/planner-guide.md и docs/github-bridge.md в репозитории koolo4/JustAI.

ЗАДАЧИ
1. Начни с плана: разбей цель на маленькие задачи — каждая на 15–60 минут и одну проверяемую цель.
2. Каждая задача — отдельный issue, заголовок начинается с «[justai]». В описании:
   - Цель (1–2 предложения).
   - Требования — нумерованно и конкретно: файлы, функции, тексты, цвета, поведение.
   - Готово, когда — как проверить.
   - Не делать — чего не трогать.
   Исполнитель — небольшая локальная модель (~9B) без памяти о других задачах: всё нужное пиши в саму задачу.
3. Как писать, чтобы модель справилась:
   - файл до ~400 строк давай ЦЕЛИКОМ: «замени всё содержимое css/style.css на текст ниже, инструментом write_file» + полный текст;
   - «добавь в конец файла» пиши именно так (есть режим append);
   - новые возможности — новыми файлами, а не переписыванием старых;
   - если просишь заменить фрагмент — цитируй его полностью, с селектором/именем функции, чтобы он был единственным в файле;
   - одна задача — один-два файла.
4. Можно выложить весь план сразу: если задача опирается на другие, последней строкой «Depends on #N, #M».
   Она начнётся только после слияния этих задач. Две задачи, меняющие один файл, — только через Depends on.
   Задача с правками к уже открытому PR (не задаче JustAI) — строка «Base: #N»: иначе ветка задачи делается
   от основной, и файлов из этого PR в ней нет.
   Агент работает по порядку: прочитать названные файлы (каждый один раз) → править → проверка → отчёт.
   Поэтому называй в задаче файлы и проверочную команду.

ПРОВЕРКА — ГЛАВНОЕ
5. Отчёт JustAI в issue задачи содержит: «Проверки проекта» (их запускает сам JustAI — им верь больше, чем словам агента),
   «Изменения в ветке» (по git — сверяй с тем, что агент заявил), ссылку на PR.
6. Поведение приложения проверяй СЦЕНАРИЕМ: issue, в описании строка «/justai e2e #N» (N — задача) и блок:
   ```yaml
   name: Главный экран
   steps:
     - screenshot: { name: menu, width: 1280 }
     - click: '#start-button'
     - expectVisible: '#game'
     - expectText: { selector: '#title', contains: 'Раунд 1' }
     - press: Escape
     - expectVisible: '#menu'
     - screenshot: { name: menu, width: 375 }
     - expectNoConsoleErrors:
   ```
   ПК1 выполнит его механически, без нейросети, и пришлёт таблицу шагов с фактическими значениями, скриншоты,
   ошибки консоли, время загрузки и изменения внешнего вида с прошлого прогона. Вердикт достоверный.
   Шаги: open, click, type, press, select, wait, waitFor, expectText (contains/equals/matches), expectVisible, expectHidden,
   expectClass (has/any), expectCount (equals/min/max), eval (code/expect), screenshot (name/width/fullPage), viewport,
   expectNoConsoleErrors, run (command/expectExit/expectOutput), window (настольная Windows-программа: command/title).
   Правила: селекторы по id и data-атрибутам; после каждого действия — проверка; у скриншотов понятные имена и ширина;
   последним шагом expectNoConsoleErrors.
7. Сайт с index.html в корне ПК1 запускает сам. Для npm-проектов поставь задачу создать justai.app.json:
   {"install": "npm ci", "start": "npm run dev -- --port 5173", "url": "http://localhost:5173"}.
8. Постоянные сценарии поставь задачей в tests/e2e/*.yml — они прогоняются перед каждым слиянием, упавший не даст слить PR.
   После правки сценариев сначала «/justai e2e #N check» — проверка формата без запуска (ошибки с номером шага).
9. Быстрая команда: issue, первая строка «/justai run #N node tests/smoke.js» — придут код выхода и вывод.
   В e2e, run и app вместо задачи можно указать номер открытого PR: «/justai e2e #113 all» проверит ветку этого PR.
   Для проверки готового PR это лучше, чем ставить агенту задачу «проверь PR».

ПРАВКИ, ОСТАНОВКА, УБОРКА
10. Правки — issue со строкой «/justai #N» и текстом правок ниже (что, где, как должно быть).
11. «🚧 заблокирована» — агент перечитывал файлы без правок: ответь issue «/justai #N» с точными заменами или полным текстом файла.
    «⏳ модель не отвечает» — ничего не делай, задача продолжится сама.
    Застрял (одна ошибка повторяется в комментарии «работает над задачей») — issue «/justai stop #N».
    Продолжить — issue «/justai continue #N» с указаниями. Больше 3–4 кругов правок — поставь новую задачу с полными файлами.
12. Лишние issues — «/justai close #2 #3». Жив ли ПК1 и что в очереди — «/justai status».
    Нет ответа на команду больше 5 минут — один issue «/justai status»; не создавай одну и ту же команду повторно.

СЛИЯНИЕ
13. Когда отчёт хороший, «Проверки проекта» зелёные и сценарий e2e дал PASS — issue «/justai merge #N».
    JustAI заново запустит проверки и сценарии tests/e2e и сольёт PR; задачи с «Depends on #N» начнутся сами.
14. «Конфликт» — правка «влей основную ветку в эту ветку и разреши конфликты», затем снова merge.
    «Проверки не прошли» — попроси исправить, затем снова merge.

ОТЧЁТ ЧЕЛОВЕКУ
15. После каждого шага коротко пиши человеку: что поставлено, что в работе, что слито, что застряло и почему.
    Не выдумывай результаты: опирайся только на ответы JustAI в issues.
````

## 2а. Если планировщик GitHub только читает (вариант C)

Добавьте к промпту из раздела 2:

````
У тебя доступ к GitHub только на чтение: создавать issues ты не можешь. Поэтому все задачи и команды выдавай
одним текстом для человека — он вставит его в ленту JustAI, и JustAI создаст issues сам, по порядку.
Формат: каждый issue начинается строкой «### ISSUE». Дальше:
- для задачи: первая строка — заголовок «[justai] …», ниже — описание по правилам из раздела «ЗАДАЧИ»;
- для команды: первая строка — сама команда («/justai e2e @2», «/justai merge #14», «/justai close #3 #4»), ниже — сценарий или текст.
Номеров новых issues ты заранее не знаешь — ссылайся на блоки этого же текста как @1, @2, … (по порядку):
«Depends on @1», «/justai e2e @2». JustAI заменит их на настоящие номера. На уже существующие issues ссылайся как #N.
Результаты читай в репозитории: отчёты JustAI — в комментариях issues, код — в ветках и pull requests.
Пример:

### ISSUE
[justai] Каркас сайта
Цель: …

### ISSUE
[justai] Экран игры
Цель: …
Depends on @1

### ISSUE
/justai e2e @2
```yaml
steps:
  - click: '#start'
  - expectVisible: '#game'
```
````

Человек копирует ответ планировщика целиком в поле внизу «Ленты моста» — кнопка станет «Создать N issues из плана». Одиночную команду (`/justai merge #14`) тоже можно вставить в это поле: она создаст служебный issue.

### Пример задачи

```
Заголовок: [justai] Страница «Контакты»

Цель: добавить страницу контактов, доступную из меню.

Требования:
1. Создай файл contacts.html в стиле index.html (тот же <header> и css/style.css).
2. На странице: заголовок «Контакты» (id="contacts-title"), e-mail info@example.com ссылкой mailto,
   форма: поле имени (id="name"), сообщение (id="message"), кнопка «Отправить» (id="send").
3. По нажатию «Отправить» под кнопкой появляется «Спасибо!» (id="thanks") — создай js/contacts.js.
4. В index.html добавь в конец <nav> ссылку <a href="contacts.html" id="nav-contacts">Контакты</a>.

Готово, когда: страница открывается из меню, после нажатия кнопки видно «Спасибо!», в консоли нет ошибок.

Не делать: не менять остальные файлы.

Depends on #12
```

### Пример проверки

````
Заголовок: E2E: страница «Контакты»

/justai e2e #13
```yaml
name: Контакты
steps:
  - click: '#nav-contacts'
  - expectText: { selector: '#contacts-title', equals: 'Контакты' }
  - type: { selector: '#name', text: 'Тест' }
  - type: { selector: '#message', text: 'Привет' }
  - click: '#send'
  - expectVisible: '#thanks'
  - screenshot: { name: contacts, width: 1280 }
  - screenshot: { name: contacts, width: 375 }
  - expectNoConsoleErrors:
```
````

## 3. Почему так (проверено на практике)

- Модель ~8B надёжно делает «запиши файл с этим содержимым» и плохо — «найди и поправь кусок»: одна задача с точечными правками заняла 11 запусков, та же работа полными файлами — 3 минуты. Отсюда — файлы целиком, append, новые файлы.
- Проверка силами агента (`[justai-test]`) ненадёжна: модель обрывалась или писала PASS без действий. Сценарий `/justai e2e` выполняется программой — первый же прогон на сайте дал 13/13 шагов за 2 секунды и скриншот игрового экрана.
- Отчёт агента может расходиться с кодом — поэтому есть «Изменения в ветке» и «Проверки проекта», которые собирает сам JustAI.
- Модель может потерять `;` перед `(function …)`: файл проходит `node --check`, но падает при запуске. Логику проверяй запуском — шагом `run` или сценарием.
- Если агент «замолчал» (пустые ответы) — обычно в задаче назван несуществующий инструмент. Инструменты агента в задаче: `read_file`, `write_file`, `edit_file`, `list_dir`, `glob`, `grep`, `run_command`, `read_output`, `kill_process`, `git_status`, `git_diff`, `todo_write`. Браузера у него нет: интерфейс проверяет мост сценарием `/justai e2e` (у задач-проверок `[justai-test]` браузер есть).
- Окно локальной модели небольшое (9216 токенов): описания лишних инструментов съедали его, история сжималась после каждого шага, и агент забывал прочитанное — отсюда «перечитывание по кругу» в kaitos #130. Теперь у задачи только нужные инструменты, а оценка окна сверяется с настоящим счётом токенов.

## 4. Инструменты профиля Architect (вариант A)

| Инструмент | Что делает |
|---|---|
| `github_create_task(title, body, depends_on?)` | задача; `depends_on` — номера задач, после слияния которых она начнётся |
| `github_list_tasks()` | открытые задачи и их состояние |
| `github_review_task(issue)` | последний отчёт, результаты команд и дифф PR |
| `github_request_changes(issue, comment)` | правки комментарием |
| `github_e2e(title, scenario, of_task?)` | сценарная проверка (YAML) — механически, со скриншотами |
| `github_run_command(command, task?)` | одна команда в ветке задачи |
| `github_merge_task(issue)` | принять: проверки и сценарии заново, слияние |
| `github_test_task(title, steps, of_task?)` | проверка силами агента (менее надёжна, чем `github_e2e`) |

## 5. Чего JustAI не сделает (и это нормально)

- Не выполнит разрушительные команды без человека (`git push --force`, `rm -rf`, реестр, выключение) — обойдёт или напишет в отчёте.
- Не сольёт PR, если проверки или сценарии красные, если задача не в состоянии «готов PR» или если на ПК1 выключено `JUSTAI_GITHUB_MERGE`.
- Не возьмёт задачи от чужих аккаунтов; публичный репозиторий — только если на ПК1 включено `JUSTAI_GITHUB_ALLOW_PUBLIC`.
- Не сотрёт незакоммиченные изменения человека в папке проекта: уберёт их в `git stash` и напишет об этом в issue (или будет ждать, если `JUSTAI_GITHUB_AUTO_STASH=off`).
- Приложения и сценарии — только на localhost; в отчёт попадают только окна запущенных им программ.
